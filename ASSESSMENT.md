# ATHARX — Architecture Assessment & Redesign Plan

Written before the enterprise-engagement-engine refactor, per the mandate to
inspect before rewriting. This is the "reverse-engineered business objective"
read of the existing MVP plus the concrete plan for evolving it — not a
rebuild-from-scratch.

## 1. Current architecture

Next.js 15 App Router monolith. Layering is already sound and worth keeping
as the skeleton: `route handler → service → repository → SQLite`, with a
`TelecomProviderAdapter` interface isolating the mock Omantel integration.
Auth is dual bearer-or-session. Client is a single customer-facing app; there
is no admin surface at all today.

## 2. Existing features

Signup (+1 Coin), Omantel prepaid package catalog, subscription flow
(MSISDN-keyed identity resolution, idempotent, auto-provisions a customer if
none exists), a reward ledger, a campaign table that only feeds the
subscription-reward lookup, a VIP milestone (65 Coins), a Lucky Draw
(entries + server-side crypto-random draw + audit tables), and Spin & Win
(1 Coin, 24h server-enforced cooldown, idempotent).

## 3. Existing domain model

`customers → subscribers → subscriptions → packages`, `rewards` (ledger),
`campaigns` (flat: one type, one reward_coins, optionally one package_id),
`reward_milestones`, `prizes`, `lucky_draws` (+entries/runs/winners),
`spin_campaigns` (+transactions), `transactions`, `api_requests`,
`analytics_events`.

**What's missing relative to the new mandate:** no `Enterprise` entity
(Omantel is implicit, hard-coded into copy, not a row); no `Behaviour`
concept (a campaign *is* its own trigger — "PACKAGE_SUBSCRIPTION" is baked
into the campaign row rather than being a reusable, configurable rule); no
`Token` concept at all — a subscription reward is credited directly to the
Coin ledger with nothing uniquely identifying *that qualifying event* as its
own traceable unit; no generic event-ingestion API (the only "event" is a
literal HTTP subscribe call); no `SelectionRun`/`SelectionResult` — the
Lucky Draw's own draw mechanic is bespoke to Lucky Draw rather than a
reusable selection engine a general campaign could also use; no simulated
customer base — only demo signups.

## 4. Retain as-is

The layering (route → service → repository), the `TelecomProviderAdapter`
pattern, the reward ledger as a derived-balance append-only table (Rule
5/6), MSISDN normalization + uniqueness rules, the idempotency pattern
(unique key + synchronous SQLite transaction), the VIP milestone model, the
Lucky Draw's entries/runs/winners audit shape (it's the right shape for
`SelectionRun`/`SelectionResult` — see below), Spin & Win's cooldown state
machine verbatim (it already meets every stated rule).

## 5. Refactor

- **`campaigns`** — today conflates "a rule" (SIGNUP, PACKAGE_SUBSCRIPTION)
  with "a reward" (reward_coins) with no enterprise, no segment, no capacity,
  no experience payload. Split into `behaviours` (the reusable trigger rule)
  + `campaigns` (enterprise, segment, qualifying behaviour, token capacity,
  reward/experience, selection method, lifecycle status).
- **Reward crediting on subscribe** — currently
  `subscriptionService.subscribe` calls `campaignService.getSubscriptionReward`
  and credits Coins directly. This bypasses any notion of a traceable
  qualifying event. Refactor so subscription (and, later, recharge) emits a
  **behaviour event** through the same pipeline the new Simulator uses —
  one code path, not two.
- **Lucky Draw draw execution** — `luckyDrawService.executeDraw` already does
  exactly what a `SelectionRun` should do. Generalize it: `lucky_draw_runs`/
  `lucky_draw_winners` become the first implementation of
  `selection_runs`/`selection_results`, addressable by any campaign, not
  only a lucky draw.

## 6. Redundant / not building

Nothing existing is redundant enough to delete — Spin & Win, VIP, Lucky Draw
all map cleanly onto the new model as *specific campaign types* rather than
special-cased features. Per §55 of the brief: no blockchain, no payments, no
real Omantel integration, no ML — none of that was built and none is being
added now.

## 7. Token vs Coin — the concrete rule

| | Token | Coin |
|---|---|---|
| What it is | A unique record of **one qualifying event** for **one campaign** | A fungible loyalty balance |
| Format | `{ENTERPRISE}-{YY}-{CAMPAIGN_CODE}-{SEQUENCE}`, e.g. `OMT-26-F1-000001` | An integer ledger sum |
| Cardinality | One per qualifying event | Accumulates across everything |
| Table | `tokens` (own row, own status lifecycle) | `rewards` (existing ledger, unchanged) |
| Who reads it | Campaign/selection engine (eligibility pool for a draw) | VIP progress, navbar balance |
| Generated by | Server, on a qualifying behaviour event | Server, as a *side effect* of a token being issued (campaign-configured amount) |

A single qualifying event therefore commonly produces **both**: one Token
(campaign participation) and N Coins (loyalty currency) — two rows in two
tables, never one merged field.

## 8. Campaign lifecycle

`DRAFT → ACTIVE → PAUSED → ACTIVE → CLOSED → COMPLETED` (selection executed).
A campaign defines: enterprise, segment, qualifying behaviour, token
capacity, reward/experience, selection method (`ALL_ELIGIBLE` for
straightforward reward campaigns vs. `RANDOM_DRAW` for a Lucky-Draw-style
campaign), and dates. Behaviour events are only accepted while `ACTIVE` and
under capacity.

## 9. Proposed domain model (additive, not a rewrite)

```
enterprises, behaviours, behaviour_events, tokens, selection_runs,
selection_results
```
added alongside the existing `customers, subscribers, subscriptions,
packages, rewards, campaigns(extended), reward_milestones, prizes,
lucky_draws+entries+runs+winners, spin_campaigns+transactions`. Full DDL and
ER diagram in ARCHITECTURE.md (updated alongside this refactor).

## 10/11. User journey / admin journey

**Customer:** Home → sees Coin balance, VIP progress, Featured Experiences,
Omantel packages, Spin & Win, Lucky Draw (unchanged shape, new "experience"
framing). **Admin (new, `/control`):** Dashboard → Enterprises → Behaviours
→ Campaigns → Tokens → Simulator → Selection/Results. The Simulator is the
single most important new screen: pick a simulated customer, pick a
behaviour, enter a value, fire it, watch qualification → token → coin
happen live — this *is* the demo.

## 12. MVP scope (this pass)

P0 items from §57: domain model, campaign engine, behaviour simulator, token
engine, token↔customer relationship, reward/coin ledger (already done),
campaign selection, admin control panel. P1: keep existing customer
experience, package marketplace, subscription API, Spin & Win, 24h cooldown,
Lucky Draw, VIP milestone — all already built, now re-wired onto the new
event pipeline where it's the subscription path.

## 13. Phase 2 (not this pass)

Multi-enterprise onboarding UI, real churn model, reward economics/ROI
calculators, A/B control-vs-treatment measurement, real Omantel integration,
polish-level experience photography.

## 14. Conflicts with the brief, and the calls made (§59)

- **"Do not merge Token and Coin into one field"** — agreed and already the
  plan above; no conflict.
- **Full admin CRUD for every entity (§30–33)** — building complete CRUD UI
  for Enterprises/Behaviours/Campaigns/Tokens/Rewards as a first pass would
  crowd out the Simulator and Selection engine, which are the actual demo
  narrative (§60/§61). Call: ship **read + the specific actions the demo
  needs** (create campaign, create behaviour, run simulator, execute
  selection) rather than generic CRUD screens for all eleven admin nav
  items; note the rest as Phase 2 CRUD polish.
- **Simulated customers up to 10,000 with rich recharge history fields** —
  building this is straightforward and kept in scope, but it's seed/demo
  data generation, not a live customer-events table; keeping it that way
  avoids a redundant second "customers" concept next to the existing
  `customers`/`subscribers` tables used by the real signup flow. Call:
  simulated customers reuse the *same* `customers`/`subscribers` tables
  (flagged `is_simulated`), not a parallel schema.
